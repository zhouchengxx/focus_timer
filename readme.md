# Focus Timer v3.6 — 开发交接说明

## 1. 项目定位

这是一个面向 Windows 的极简个人时间投入记录工具。

核心设计目标不是“精细管理时间”，而是：

> 以尽可能低的操作成本，记录自己实际把时间投入到了什么事情上，并在每天、每周进行回顾。

当前版本已经从早期的桌面宠物方案回归为极简悬浮按钮，原因是桌宠动画容易吸引注意力，与“工具尽量不可见”的目标冲突。

项目坚持几个原则：

* 开始工作时不要求提前分类。
* 分类和一句话结果都在结束时填写。
* 平时不显示已经计时多久，避免时间数字本身成为注意对象。
* 左键交互尽可能简单。
* 统计用于复盘，不用于制造“效率分数”。
* 不做积分、连续打卡、效率评分、成就等容易产生生产力幻觉的功能。
* 尽量使用 Python 标准库，保持绿色版和单文件结构。

`Focus Timer v3.6`

# 3. 主界面

主界面是一个：

`40 × 40 px`

的无标题栏悬浮窗口。

关键参数：

`WINDOW_SIZE = 40`

鼠标经过时透明度：

`ACTIVE_ALPHA = 0.96`

鼠标离开后：

`INACTIVE_ALPHA = 0.60`

拖动超过：

`DRAG_THRESHOLD = 4 px`

才会被识别为拖动，否则视为点击。

悬浮窗：

* 无 Windows 标题栏；
* 默认始终置顶；
* 可以拖动；
* 自动记住上一次位置；
* 鼠标离开后自动半透明；
* 鼠标移回时恢复清晰。

# 4. 核心状态机

整个计时器只有三个状态：

`idle`

未开始。

`running`

正在计时。

`paused`

已经暂停。

对应的悬浮按钮显示：

`idle → ▶`

`running → Ⅱ`

`paused → ▶`

暂停状态仍显示播放按钮，是因为下一次左键操作是“继续”。

左键逻辑固定为：

`idle → 单击 → start()`

`running → 单击 → pause()`

`paused → 单击 → resume()`

左键不承担“结束”功能。

这个交互原则目前非常重要，后续开发尽量不要破坏：

> 左键只负责“开始 / 暂停 / 继续”。

---

# 5. 结束一段工作

结束功能只放在：

`右键 → 结束并记录...`

未开始状态下，此菜单项自动禁用。

执行结束时：

如果当前正在运行，点击“结束并记录”的瞬间立即冻结有效计时时长，并记录结束时间。

之后用户填写类别和一句话结果所花费的时间，不计算进工作时间。

如果原来已经处于暂停状态，则此前按下暂停的时间作为结束时间。

如果打开填写窗口以后选择取消：

* 原本正在运行 → 恢复运行；
* 原本已经暂停 → 保持暂停。

因此不会因为打开填写窗口而污染有效计时时间。

# 6. 结束记录窗口 FinishDialog

结束一段工作以后弹出 `FinishDialog`。

用户只填写两个信息：

`类别`

例如：

核心项目
日常事务
学习
临时事务
生活/恢复

类别也允许直接输入新的类别。

`结果`

一句话描述本次投入产生了什么。

例如：

`完成第一版数据分析`

或者：

`看完注意力机制，并整理了核心概念`

这里刻意不记录：

* 效率评分
* 专注程度
* 情绪
* 精力分数
* 完成百分比

目的仍然是保持记录足够轻。结束窗口同时显示本次有效投入时长，并自动记住上一次使用的类别。

# 8. SQLite 数据结构

数据库文件：

`focus_timer.db`

目前主要有四张表。

## sessions

保存已经完成的正式记录。

字段：

`id`

主键。

`category`

事务类别。

`started_at`

开始时间，ISO datetime 字符串。

`ended_at`

结束时间。

`duration_sec`

实际有效投入秒数。

`note`

一句话结果。

特别注意：

`duration_sec` 不一定永远等于 `ended_at - started_at`。

原因是计时过程中可能暂停。

因此统计有效投入时，必须以：

`duration_sec`

为准。

---

## categories

保存用户使用过的类别。

字段：

`name`

`sort_order`

---

## settings

保存简单的软件状态。

目前主要使用：

`window_position`

记录悬浮窗位置。

`last_category`

记录上一次使用的事务类别。

---

## active_state

保存当前尚未正式结束的计时。

字段：

`session_started_at`

`elapsed_sec`

`status`

`paused_at`

其中状态只能是：

`running`

或：

`paused`

这张表用于异常退出以及主动退出后的恢复。

# 9. 计时方式

实际计时使用：

`time.monotonic()`

而不是直接用系统当前时间做持续时间计算。

有效时间：

`accumulated + (time.monotonic() - run_started_mono)`

这样可以避免用户修改 Windows 系统时间导致当前计时发生跳变。

开始时：

* 记录 `started_at`
* `accumulated = 0`
* 保存 monotonic 起点
* 状态切换为 `running`

暂停时：

* 将当前 elapsed 累加到 `accumulated`
* 清除运行起点
* 记录 `paused_at`
* 状态切换成 `paused`

继续时：

* 保留 accumulated
* 建立新的 monotonic 起点
* 状态重新变成 `running`。

---

# 10. 自动恢复机制

程序运行期间，如果处于 `running`：

每约 5 秒把当前计时状态写入 `active_state`。

因此即使程序异常关闭，最多通常只损失几秒记录。

下一次启动时，如果发现 `active_state`：

弹窗询问：

`是否恢复？`

如果恢复：

原状态是 paused：

继续保持暂停。

原状态是 running：

从“软件重新打开的这一刻”继续运行。

非常重要：

> 软件关闭期间的时间不会计入有效工作时间。

因此例如：

17:00 软件关闭
第二天 09:00 打开

不会把这 16 小时算成工作。

# 11. 主程序退出逻辑

如果当前没有任务：

直接退出。

如果存在未结束任务：

弹出三个选择：

`是`

结束并记录。

`否`

保存现场并退出。

`取消`

继续运行软件。

选择“保存现场并退出”后，下次启动可以恢复。

# 12. 统计窗口

`统计...`

目前支持：

`今天`

`本周`

统计范围定义：

今天：

统计顶部显示：

`各类别有效时间 + 占比`

例如：

`核心项目 8h 20m (48%)`

这里的比例以有效时长 `duration_sec` 为基础。

`一句话结果`

`started_at DESC`

# 14. 手动新增记录

统计窗口底部有：

`新增记录`

用于：

* 没在电脑旁；
* 忘记点开始；
* 外出工作；
* 阅读；
* 开会；
* 运动；
* 其他没有通过悬浮计时器记录的投入。

新增窗口需要：

`日期`

格式：

`YYYY-MM-DD`

`开始`

格式：

`HH:MM`

`结束`

格式：

`HH:MM`

`类别`

`结果`

新增记录默认时间为：

当前时间往前一小时 → 当前时间。

类别默认使用最近一次类别。

---

# 15. 跨午夜逻辑

手动记录支持：

`23:30 → 00:40`

程序自动认为结束时间属于第二天。

因此有效时长：

`1h 10m`

如果：

`开始时间 == 结束时间`

则不会自动解释成 24 小时，而是提示输入有误。

这样可以避免无意生成 24 小时记录。

支持：

`今天`

`本周`

`本月`

`本月暂不生成 Markdown。`

# 18. 每日 Markdown 格式

格式：

```text
# 2026-08-29

- 14:05–15:32 · 核心项目 · 1h 27m · 完成第一版分析
- 11:20–11:55 · 临时事务 · 35m · 处理数据问题
```

如果 note 为空：

```text
- 09:30–10:45 · 核心项目 · 1h 15m
```

如果跨午夜：

```text
- 23:30–次日 00:40 · 学习 · 1h 10m · 阅读资料
```

Markdown 使用的仍然是数据库里的正式记录，并保持统计界面“最新记录在前”的顺序。

- 10:10–11:30 · 核心项目 · 1h 20m · 完成方案

# 23. 当前设计中最好不要轻易破坏的原则

第一，开始必须零摩擦。

不要重新加入：

“开始前先选择类别”。

分类应该发生在结束以后。

第二，悬浮窗不要显示计时时长。

用户应该关注当前事务，而不是：

“我已经工作了多少分钟”。

第三，左键只负责：

开始 / 暂停 / 继续。

结束放在右键菜单。

第四，不做持续动画、桌宠等容易夺取注意力的视觉元素。

第五，数据统计应该帮助复盘，而不是变成新的任务。

第六，不加入复杂的效率评分体系。

第七，尽量保持本地 SQLite + 单文件 Python + 标准库。

第八，统计数字代表“投入”，不能冒充“成果”。

因此一句话结果仍然很重要。

# 24. 当前版本已经解决的问题

从最早方案发展到 v3.6，目前已经解决：

计时开始摩擦过大 → 开始无需分类。

悬浮窗面积过大 → 缩到 40×40。

持续显示时间影响注意力 → 完全不显示时间。

桌宠容易吸引注意力 → 去除宠物。

暂停后不能继续 → 已支持暂停 / 继续循环。

如何结束与继续冲突 → 结束独立放入右键菜单。

忘记记录 / 不在电脑旁 → 支持手动新增。

错误记录难修复 → 支持编辑。

跨午夜记录 → 自动处理。

Markdown 导出产生额外文件负担 → 改为统计界面直接预览 + 一键复制。

# 25. 后续可能的开发方向

目前软件已经进入“可以稳定使用”的阶段。

因此后续新增功能应优先来自真实使用过程中出现的摩擦，而不是为了功能丰富而添加。

比较合理的候选方向包括：

**记录类别管理**

例如允许：

* 重命名类别
* 删除不再使用的类别
* 调整类别顺序

目前数据库已经有 `sort_order`，但还没有专门的类别管理 UI。

**统计窗口进一步减负**

例如：

* 记住上一次选择的是今天还是本周
* 记住统计窗口大小和位置

**Markdown 格式优化**

应根据实际复制后的用途决定，而不是提前增加复杂字段。

**备份**

如果长期积累的数据开始有价值，可以考虑增加非常轻量的：

`备份数据库`

本质只是复制 `focus_timer.db`。

暂时不建议做：

* 大量图表
* 热力图
* 打卡
* 成就系统
* AI 自动评分
* 效率评分
* 自动监控窗口
* 自动判断正在做什么
* 桌宠
* 复杂项目管理

除非后续真实使用明确证明它们可以减少负担。
